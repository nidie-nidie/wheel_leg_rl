# 动作饱和与奖励贡献核对

已完成用户指定的前两项诊断。当前证据更支持先检查“右腿长期处于动作裁剪边界，以及腿部罚分如何分配”，暂不支持直接删除轮动作历史、继续加大六维 action_smooth，或只把加速度预算百分比向下调。

这次发现的是明确的行为和奖励分配现象，尚未证明它们是左腿抽搐的唯一原因。

## 范围与证据

- 对照：同一组预算搜索中的 baseline 与 85% 模型，各八个既有 MuJoCo 场景；另核对 85% 键盘控制记录。
- 17 条轨迹，共 10,120 个控制步、202,400 个物理步。控制步长 0.02 s，物理步长 0.001 s。
- 对既有场景 CSV，以及键盘记录的 history、网络动作和运动数据进行复现，所核对字段最大误差为 0。
- 场景稳态窗口为 2–10 s；键盘站立窗口为 2–20 s，指令为 vx=0、yaw=0、height=0.2 m。
- 读取 baseline、80%、85%、90% 四组已有 TensorBoard 数据，每组 200 iteration；主要统计最后 50 iteration。未运行 Isaac、未训练。
- 本次只在此诊断目录新增脚本、数据、图表和报告。160 个受保护文件的 SHA256 保持一致，没有调用子 agent。

## 第一项：动作饱和和左右姿态

### 右腿目标长期固定在动作下边界

85% 模型在八个场景的稳态窗口中，右腿前驱 jAB、后驱 jAG 的原始动作都低于 -1，负向裁剪率均为 100%。两个电机目标角一直分别为 -39.17148°、-0.93556°。

这是“策略动作被裁剪为 -1”，不是关节碰到了机械限位。所有分析稳态窗口的腿关节软限位罚分均为 0，实际关节也没有达到 ±1 rad 的机械限位。

键盘站立记录：

| 项目 | 左前 jIJ | 左后 jIO | 右前 jAB | 右后 jAG |
|---|---:|---:|---:|---:|
| 原始动作平均值 | 0.507 | 0.007 | -4.560 | -4.903 |
| 动作裁剪率 | 0% | 0% | 100% | 100% |
| 电机目标角变化范围 | 6.186° | 5.322° | 0° | 0° |
| 实际角度 P5–P95 范围 | 1.974° | 2.254° | 0.350° | 0.151° |
| 实际角加速度 RMS | 25.760 | 28.142 | 8.360 | 5.300 |

加速度单位为 rad/s²。右腿原始动作仍在变化，但这些变化全部被裁剪成相同的 -1，因此不会改变右腿目标角。右腿实际角度仍有小幅运动，来自恒定目标下的物理响应，不能据此说右腿完全不动。

这解释了目前看到的左右行为差异：左腿目标在持续变化，而右腿目标基本不参与变化。它尚不能证明右腿饱和直接引起左腿抽搐。

### 不对称并非只存在于 85% 设置

baseline 的 jAB 在八场景也均为 100% 负向裁剪；jAG 七场景为 100%，高站立场景为 95.75%。所以这种现象不是仅有 85% 加速度设置才出现。

| 场景 | 85% 右腿两动作负向裁剪率 | 85% 左右 phi0 平均绝对差 |
|---|---|---:|
| nominal_stand | 100% / 100% | 25.79° |
| low_stand | 100% / 100% | 28.41° |
| high_stand | 100% / 100% | 23.56° |
| forward | 100% / 100% | 33.65° |
| reverse | 100% / 100% | 25.74° |
| left_turn | 100% / 100% | 24.71° |
| right_turn | 100% / 100% | 26.98° |
| combined | 100% / 100% | 29.50° |

键盘站立中，左右 phi0 平均约 84.89° / 110.69°；虚拟腿长约 0.1704 / 0.1944 m；身体平均 roll / pitch 约 1.68° / 1.19°。这些说明姿态存在持续不对称，不能仅凭此指定一个理想对称姿态。

同时，两轮平均接触法向力约 22.07 / 21.33 N，左侧占总平均法向载荷 50.86%。现有数据不支持“左腿明显承担了绝大多数静态载荷”这个解释。接触力读数来自每个控制周期最后一次求解，时间在最后一次积分之前 1 ms；它不是完整的平衡贡献分析。

### 动作分布与裁剪范围需要关注

最终模型右腿训练动作标准差约为 0.967 / 1.011。以记录中的 MuJoCo 状态和动作均值为条件，按原有高斯分布计算，右腿采样进入 (-1,1) 区间的平均概率仅约 0.01190% / 0.00743%。

这是针对这些 MuJoCo 状态的计算，不能直接当成 Isaac 训练中的实测概率。它说明策略均值已经深入裁剪范围以外；不是稍微超过 -1。PPO 仍然能够改变均值，不能说裁剪让策略完全无法学习。

## 第二项：奖励贡献与自适应增益

### 六维 action_smooth 的主要罚分来自轮子

现有公式保持不变：六维已裁剪策略动作的二阶差分平方和。

在键盘站立窗口，将同一个公式按通道拆开统计：

| 现有罚分项 | 左腿贡献 | 右腿贡献 | 两轮贡献 |
|---|---:|---:|---:|
| action_rate | 0.339% | 0% | 99.661% |
| action_smooth | 0.340% | 0% | 99.660% |
| 六关节 dof_acc | 3.112% | 0.210% | 96.678% |

这里仅做诊断分账，没有拆改奖励项。

因此，action_smooth 确实计算并加入了奖励，但在这条轨迹上主要衡量轮子指令反复变化。腿部较小的归一化指令变化仍能造成明显的实际机械抖动；六维动作平滑度与腿部实际角加速度不是同一个量。把六维权重加倍，也会主要增加轮子承担的罚分。

右腿的目标角恒定，所以右腿动作平滑罚分为 0 是这个公式的正常结果。它不等于右腿没有实际角加速度。

### 新加的腿部加速度罚分也主要来自右腿

85% 的预算分别为：
jIJ=34.1448、jIO=32.6121、jAB=5.9808、jAG=4.2275 rad/s²。

代码针对每个关节计算 max(a_j² / budget_j² - 1, 0)，再对四关节求和。预算来自历史模型的左右各自参考值，因此左右容许尺度相差较大。当前表现较安静的右腿，对其较低预算而言，反而产生更大的归一化超额。

键盘站立重算中，新加速度罚分分配约为：

- 左腿：13.72%。
- 右腿：86.28%。

已有训练日志最后 50 iteration 的平均分配约为：

| 关节 | 加速度罚分占比 |
|---|---:|
| jIJ | 4.02% |
| jIO | 5.17% |
| jAB | 30.94% |
| jAG | 59.87% |

训练与 MuJoCo 数字分别统计，不能混为同一批数据。训练是随机采样动作和随机化环境，MuJoCo 部署使用确定性动作。

### 增益几乎一直达到上限

80%、85%、90% 三组均为：
首 iteration 使用 gain=0，完成首次 rollout 后达到 1；此后 199 iteration 使用的 gain 全部为 1。每组 200 iteration 中，决定最大平均超额的关节均是 jAG。

原有更新公式是 min(max_j(mean_excess_j)²,1)。当任一关节的 rollout 平均超额 ≥1 时，增益达到上限。这些训练数据持续满足该条件。

因此，本次参数设置下，自适应项实际接近“固定最大增益罚分”，没有展示持续自动调节增益的优势。这是对当前试验配置的判断，不是对完整 ROGER 论文方法的否定。

85% 最后 50 iteration 的每控制步加权平均值：

| 项目 | 加权平均值 |
|---|---:|
| tracking_vx | +0.034663 |
| tracking_vx_enhance | -0.001058 |
| phi0_symmetry | -0.004546 |
| orientation | -0.004024 |
| action_rate | -0.000509 |
| action_smooth | -0.001242 |
| dof_acc | -0.000256 |
| 新腿部 leg_acceleration | -0.012114 |

新腿部加速度罚分是 action_smooth 的约 9.76 倍，约 90.81% 又来自右腿。不能把当前问题简单理解成“惩罚没加进去”或“总惩罚太轻”。

## 结论与下一步优先级

现有证据确认了：
1. 右腿两个目标长期恒定在动作裁剪下边界；左右运动和姿态持续不对称。
2. 六维平滑罚分主要来自轮子，新腿部加速度罚分主要来自右腿。
3. 当前自适应增益长期达到上限，未形成持续自动调权过程。

更值得优先研究的是：策略为什么长期采用右腿饱和的动作分布，以及加速度预算的归一化尺度是否把主要罚分分配到了与左腿抽搐不一致的位置。

本次不建议直接删除轮动作历史、取消动作或力矩边界、继续增大六维 action_smooth，或只继续降低预算百分比。后续若做训练对照，应分别隔离动作分布/饱和与罚分分配这两个变量，避免一次同时改动多项。

这些数据尚未证明唯一因果、未证明左右预算应该强行相等，也没有给出安全阈值或已经验证的修复方案。

## 复现与文件

在仓库根目录依次运行：

1. wheelleg_dreamwaq/sim2sim/mujoco/.venv/Scripts/python.exe 本目录/capture.py
2. .venv/Scripts/python.exe 本目录/analyze.py
3. .venv/Scripts/python.exe 本目录/verify.py

capture-verification.json 保存逐轨迹复现误差；analysis.json 保存全部统计与 checkpoint 增益状态；trajectories.npz 保存补充状态；weighted-rewards.npz 保存奖励重算；saturation-reward-audit.png 展示两腿目标、实际运动、训练罚分分配和增益轨迹；verification.json 保存独立核对结果。

MuJoCo 奖励重算使用原有 reward 函数与导出时的训练权重，按原 runtime 读取动作后的状态；增益固定为训练日志中的上限 1；原轨迹均存活，termination 为 0。它不是在 MuJoCo 中重新运行 PPO，也不等于复现 Isaac 的逐步奖励；两边 actuator 力矩读数的获取方式也不同。
